# Security review (Phase 5)

A pass over the API, website and app before the first real users. Each item lists what protects it and where.

## Checked and in place

- **Login.** OTPs are stored as HMACs with a server pepper, expire in 5 minutes, allow 5 wrong tries, and at most 5 texts per phone per hour. Sessions are random tokens stored as SHA-256 hashes and last 30 days. Nobody can make themselves admin; only phones in `ADMIN_PHONES` (and accounts granted admin on the server with `admin:grant`) are admins, and removing a phone from `ADMIN_PHONES` takes admin away from its next request, including live sessions; it drops to owner. Stub OTP is refused in production. (`apps/api/src/services/auth.ts`)
- **Login without SMS (PRP-01).**
  - Phone and password with argon2id, 15–128 characters, a blocklist, and generic errors that don't reveal whether a phone has an account.
  - A per-phone lockout (5 tries, then 15 minutes) that also covers phones with no account and parallel guesses.
  - Invites and `ADMIN_PHONES` need an OTP-verified phone.
  - Demo accounts are refused on every session path of a production standard instance, and a demo instance admits only demo accounts.
  - `db:reset` refuses in production. (`apps/api/src/services/auth.ts`, `apps/api/test/auth-modes.test.ts`)
- **Who can do what.** Every non-public route has a role guard. Owner actions load the hostel, room, residency, review or visit through its owner, so one owner can't touch another's data. Residents can only see issues, posts and the neighbour list of a hostel they live in. Anyone signed in may take a plan, but never at a hostel they own, so an owner can't bill themselves or become a verified reviewer of their own hostel. Covered by the API tests. (`apps/api/src/services/access.ts`)
- **Payments.** Razorpay payment and webhook signatures are checked in constant time after a length check. Marking a bill paid is idempotent, so a webhook and the checkout callback can both arrive safely. Simulated payments are refused on any instance with Razorpay keys and on every production standard instance, and stub signatures are refused there too. (`apps/api/src/services/payments.ts`, `apps/api/test/payment-modes.test.ts` › a live instance refuses simulated payments and stub signatures)
- **Payment records (PRP-04, edge cases M1 and M3).** Every tenant and owner bill records how it was settled in `payment_mode`: `razorpay_live` (keys starting `rzp_live_`, the only real money), `razorpay_test` (`rzp_test_` or any other key), `simulated` (no keys, the simulate button, stub-signed checkouts, and any order the stub created even if keys are set later) or `waived` (an admin waived an owner bill; it stays void). Check constraints keep `paid` and the mode in step. Payouts, platform revenue, the owner's payouts and insights count `razorpay_live` only and show what they left out; waived bills are never revenue. A payment that arrives after its bill stopped being payable is never only logged: the first bill of a plan whose bed hold expired is revived when a bed is still free, otherwise a `payment_exceptions` row (one per Razorpay payment id) records the refund owed, the payer sees it on `/pay`, and an admin marks it refunded (audited). Concurrent deliveries are serialized on the bill row. (`services/payments.ts`, `services/refunds.ts`, `services/money.ts`; `test/payment-modes.test.ts`, `test/late-payments.test.ts`)
- **Uploads.** At most 5 MB. The file type comes from the file's first bytes, not its name or declared type, and only JPEG, PNG and WebP are kept. Every photo is decoded and re-encoded, which drops EXIF (GPS position, device, time), XMP, ICC and text chunks and anything appended after the image; the orientation is applied first. Files are served with the type of their stored extension and `nosniff`. (`apps/api/src/routes/uploads.ts`, `apps/api/src/lib/images.ts`)
- **Photos are your own uploads.** Listing, issue and community photos can only be files the caller uploaded through `POST /uploads`, attached with the receipt it returned (an HMAC over the uploader and the file key). Outside links, another person's upload, and an upload made for the other purpose are refused. (`claimUpload` in `apps/api/src/lib/uploads.ts`)
- **Private attachments.** Issue and community photos are uploaded as private (`att_` keys). The API only hands out links to them inside responses that already passed the membership check (residents, the owner, admins), and those links are signed and expire within 90 minutes. Without a valid signature the file is a 404; with one it is served `Cache-Control: private`. Listing photos (`pho_`) are public. (`apps/api/src/lib/uploads.ts`, `apps/api/test/uploads.test.ts`)
- **Website session.** The token lives in an httpOnly, SameSite=Lax cookie (Secure in production) and never reaches browser JavaScript. Forms are Next.js server actions, which check the request origin. Return paths are checked so they can't redirect to another site. (`apps/web/lib/api.ts`, `apps/web/lib/paths.ts`)
- **App to website sign-in.** The code the app uses to open the payment page is random, stored hashed, single use, and expires after 2 minutes; redeeming it is one atomic update. (`apps/api/src/services/auth.ts`)
- **Input.** Every request body and query is validated with the shared zod schemas.

## Fixed in this phase

- Food partner logo links accept only `http` and `https` URLs, so a `javascript:` or `data:` link can't be stored. (Photos went further later: they must be uploads, see below. Logos are never shown as images.)
- The website sends a Content Security Policy: scripts only from itself and Razorpay Checkout, frames only from Razorpay, images only from itself, the API (`API_PUBLIC_URL`, read at build time), OpenStreetMap tiles and Razorpay, no plugins, no framing of the site.
- The API sends standard security headers (`hono/secure-headers`), with cross-origin loading allowed only so photos can show on the website and in the app.
- Return paths (`next` on login and the app hand-off, and every form's `_back`) are parsed as URLs, so `/\evil.example` or a tab after the slash can no longer send someone to another site. (`apps/web/test/paths.test.ts`, `apps/web/e2e/handoff.spec.ts`)
- Public reviews now say how the reviewer's stay was confirmed: "Verified stay · paid through Hostels" for subscribers, "Resident · added by the hostel" for people an owner added. An owner can't quietly add friends to boost ratings without readers seeing it.

## Fixed in the backend fixes pass (M5, M6, M8–M10)

- **Overbooking.** An owner's room edit wrote back the bed count their form had loaded, giving back a bed booked meanwhile. Bed counts now move by the difference from what the form showed, in one conditional update that never frees or removes beds held by plans. (`updateRoomType` in `services/listings.ts`)
- **Payment call inside the booking.** Razorpay was called while the room row was locked. The booking now commits first; the payment order is created when the tenant opens checkout, outside any transaction, with a 15-second timeout. An unpaid plan still expires after 30 minutes and gives its bed back. (`subscribe` in `services/billing.ts`, `orderFor` in `services/payments.ts`)
- **Private photos were public.** See "Private attachments" above. Signed links were chosen over checking a session on each image request because the website shows photos with plain `<img>` tags (the session cookie lives on the website, not the API) and the app's `<Image>` would need the bearer token on every request; one signed link works the same in both.
- **Photo links froze the host.** Uploads are stored as `/uploads/<key>`, and links are built from the current `API_PUBLIC_URL` when a response is made. Older absolute links are rewritten when read, so no data migration was needed.
- **Photo metadata and outside photos.** See "Uploads" and "Photos are your own uploads" above. The demo seed draws its listing photos and stores them as uploads, so no stock-photo host is needed.

## Still open before production

- **Refunds are manual.** A payment that could not be applied is recorded and shown to admins, but the money goes back only when someone refunds it in the Razorpay dashboard and marks it here. The payer is told it comes back within `REFUND_WITHIN_DAYS` (7) days; that promise is not in the specs and needs the owner's confirmation.
- **Bills paid before migration 0008.** Rows with Razorpay-looking ids were recorded as `razorpay_test`, because no live account had been connected. An instance that took live payments before this migration must set those rows to `razorpay_live` by hand, then regenerate the affected payouts.
- **Separate webhook secrets per Razorpay mode.** The mode is taken from the key configured when a payment is confirmed. After switching an instance from test to live keys, a late test-mode checkout fails its signature check (it was signed with the test key), but a test-mode webhook would be accepted and recorded as live if both modes share one webhook secret. Give the test and live webhooks different secrets, and switch keys when no checkout is open (bed holds last 30 minutes).
- **General rate limiting.** Only OTP sending and password login are rate-limited (sign-up isn't). Put the API behind a proxy or add a limiter for login, search, issue and post creation.
- **Inline scripts in the CSP.** Next.js needs `'unsafe-inline'` for scripts without nonces. Moving to nonce-based CSP via middleware would tighten it.
- **Photo storage.** Uploads sit on the API's local disk. Move them to object storage (R2 or S3) before running more than one API instance; the CSP `img-src` then needs the storage origin. Uploads that are never attached are never deleted.
- **Photos from before the fixes.** Issue and post photos uploaded before attachments became private carry public `pho_` keys and stay reachable by their link; outside photo links in older rows are blocked by the website's CSP but still shown in the app. There are no real users yet, so resetting development databases is enough; data from a real instance would need a one-off migration.
- **Signed photo links can be shared.** Anyone given a private photo's link can open it until it expires (at most 90 minutes), including a resident who has just moved out.
- **Owner-added residents.** They are labelled on reviews, but an owner could still add people who never lived there. An owner can also backdate a resident's start date, which makes them eligible to review at once. Consider requiring a few months of rent records, or an admin spot-check, before their reviews count in the rating.
- **Secrets and HTTPS.** Real MSG91 and Razorpay keys, a long `OTP_PEPPER`, HTTPS everywhere, and database backups. See the run guide.
